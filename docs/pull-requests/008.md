Before: `kdtv-proto` computed the Saturn checksum over `ADDRESS + CONTROL + DATA_LEN + DATA` and left out `AA 55`. Every frame it would have sent carried a checksum one lower than the valves use.

After: the checksum covers every byte before it, sync included, so a whole frame sums to zero mod 256. This matches every frame captured on the installed Valve 2 bus on 2026-10-24: the idle poll `AA 55 00 07 00 FA`, the valve's replies, and the frames around a real start and stop (`AA 55 13 87 06 00 01 63 00 00 00 FD`, `… 03 01 63 00 00 00 FA`). All 102 decoded frames in #7 close this way, and none closes without the sync bytes.

The old rule rested on xagon0's `AA 55 00 02 01 1E DF`. That isn't a capture. The document's "Annotated Packet Captures" are computed from its own formula, so the example could only ever agree with it. `AA + 55 = FF`, so the two rules differ by exactly one on every frame.

How:
- `checksum()` adds `SYNC1 + SYNC2`. A new test holds 8 captured frames and checks that each one closes and its sync-excluded value is refused. Every hardcoded vector in the proto, emulator, service and telemetry crates is recomputed, along with `fixtures/saturn.json`. `dtv/` has its own checksum and is unchanged.
- `requirements.toml`: CHK-01 is now `[A]` with the sync-inclusive rule. CHK-02 is rewritten as "do not exclude", and the superseded claim is kept. CHK-03 sums from SYNC1. CHK-04 requires `0xFC` / `0xB4`. `commissioning/CHECKLIST.md` regenerated with no change.
- `controller/docs/DECISIONS.md` has a new W4 entry recording the wrong turn. `DESIGN.md` and `docs/protocols/overview.md` now state the measured rule.
- The captured frames live in a unit test, not in the fixtures. Marking fixtures `captured` would open the transmit gate, and `xtask gate-closed` still passes.
- Side effect: `AA 55 AA 55 00 02` now closes. In capture mode, a stray sync pair in front of a frame starting `00 02` decodes as a short fake frame. Strict mode refuses it by address. `a_bare_sync_pair_before_a_frame` documents this.

Merge #7 first: the new docs link to `research/diagnostics/2026-10-24-saturn-valve-bus/`, which lands there.

Not changed here, and still contradicting the capture: the bus carries addresses `0x00`, `0x01`, `0x13` and `0x1F`, against ADDR-01/02 (broadcast `0x0F`, valves `0x03..0x07`). The `0x87` write has `DATA_LEN 0x06`, not OUT-03's `0x02`.
