`cargo xtask reqs` reported `0/356` covered. The note in `reqs.rs` read that as a convention nobody had got round to adopting. It was the other way round: **the matcher could not match the names its own documentation asked for.** This fixes that, then adopts the convention for the requirements whose proof already existed in the suite.

## Why it was 0

Two faults in [`controller/crates/xtask/src/reqs.rs`](controller/crates/xtask/src/reqs.rs):

- **Coverage was an equality test.** `sources.contains(&r.slug())` accepts `req_controller_design_safe_05` and nothing else. The module doc one screen above gives `req_controller_design_safe_05_missing_response_latches_zone` as the example, and the failure message prints `` req_{slug}... `` with the ellipsis. Both promised a suffix the matcher rejected, so no name could carry a slug *and* say what it tests.
- **The scan could not see `async fn`.** It matched a bare `fn req_`, and much of the API and service suite is `#[tokio::test]`. Five `kdtv-api` tests already carried slugs and were reported uncovered anyway.

The second had already damaged the suite: `req_controller_design_api_01` exists as a separate test from `seven_of_the_eight_api_01_operations_are_performed` for no reason but to put the slug on something the scan could see — its own doc comment says so.

With both fixed the register reports **8 before any renaming**, not 0. The real gate is **182 hard software-verifiable** requirements, not the 270 hard ones — `--strict` only ever iterated the software-verifiable subset.

## What changed in the tool

- `covered_by` is a prefix match anchored on the underscore after the slug, so `req_<slug>_<description>` counts and `req_<slug>xyz` does not.
- `declaration` strips the qualifiers that may precede `fn`, so `async fn req_…` is visible.
- `slug_ambiguities` fails the run if one register slug is a prefix of another at an underscore boundary, which the new prefix match would otherwise double-credit. There are none today; this is so that adding `OUT-5-B` beside `OUT-5` breaks the build rather than quietly inflating the number.
- `claimed_slugs` lets one test name several requirements (`req_<a>_req_<b>_…`). Requirements and tests are not in bijection. Many-tests-to-one already worked (shared prefix); one-test-to-many did not, and the alternative was splitting tests — which is not a rename, and which this repo has already paid for once.

None of this widens what counts as proof. The register is still keyed on `(document, id)`, and a slug still has to appear in a test name.

## Adoption

**87 of 182** hard software-verifiable requirements now name a test, up from 8. Renames keep the original sentence; no test's assertions changed.

Every one was read before it was named. Where a test proved only part of a compound statement it was left alone, because a false traceability link is worse than none:

- **STEAM-12** is not pointed at `an_observed_power_clean_reports_pc_active` — see the defect below.
- **STEAM-16**'s "stop trusting the actual-temperature field" has no test, so the test proving the stop-and-latch half carries STEAM-15 only.
- **BOOT-06** ("only after *both* zones are confirmed off") is not claimed by the single-zone boot test proving BOOT-01 and BOOT-05.
- **DEVID-02** has no test because it has no implementation to test.

Seven register entries were reclassified using the register's own canonical `not-testable-in-software` marker. `software_verifiable()` is a keyword test over free text, and these described manual work in words it does not look for ("manual soak", "log review", "repository review"), so `--strict` was demanding a cargo test for a seven-day soak. SAFETY-03's `verification` field already said it was not unit-testable.

## A real defect, found by tracing

`SteamStateByte::is_producing()` is true for `PowerClean` (`0xCC`), and `SteamMachine::on_first_status` shuts down anything producing at boot. `STEAM-ADAPTER.md` STEAM-12 says the opposite — on a decoded `0xCC`, report `PC_ACTIVE` and *do nothing that could interrupt the cycle*, because an interrupted power clean restarts from the beginning.

Nothing here moves shower water, and a power clean is run from the generator's own control, so this is a correctness fault rather than a safety one. **Not fixed in this PR** — the change was traceability, and fixing it means deciding what a master should do when it boots into someone else's 45-minute cycle. Recorded in `STORY-LOG.md`.

## `--strict` is NOT enabled in CI

It does not pass yet, so wiring it into the `audit` job would just redden it. **95 remain**, and they split cleanly:

- **28 are not this workspace's to prove.** The whole `CGI-*`/`HTTP-*` family, `MODEL-*`, `OUTLET-*` are about the legacy HTTP client and React app in `app/`. The daemon cannot even link an HTTP client (`audit-graph` asserts it), and the scan root is `controller/crates`. Their slugs are also unusable, because `document` holds prose rather than a path for those entries.
- **67 are controller-domain** and need the same read-and-verify treatment (18 CONTROLLER-DESIGN, 12 STEAM-ADAPTER, 9 steam-generator, 8 HARDWARE-SPEC, rest scattered).

The 28 need a decision before they can be closed honestly. Marking them `not-testable-in-software` would be false — they *are* tested, by vitest — and would wrongly put them on the commissioning checklist. The options are a `workspace = "app"` field the strict gate scopes on, or extending the scan to the app's suite.
