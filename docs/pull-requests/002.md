## What this is

The controller software for the replacement master described in
[docs/replacement-controller/](docs/replacement-controller/CONTROLLER-DESIGN.md): a Rust workspace
under a new top-level `controller/` directory, targeting a Raspberry Pi 4 driving two Saturn valve
buses and one DTV+ steam link, with an end-to-end suite that drives the real daemon binary and needs
no hardware.

Complete. Eleven crates, 809 tests, and CI covering all of it including the end-to-end ring.

## Safety position

**No valve traffic and no water actuation have been performed.** Every Saturn and DTV+ frame here is
tier `[C]` — third-party reverse engineering, unverified against this installation. The DTV+ side is
weaker still: no DTV+ bus has ever been captured in this project, and the reference system reports
`steam_installed = false`, so the steam codec has never seen a real device.

That is enforced rather than asserted. The **transmit gate** is checked at two boundaries — the
encoder cannot be constructed without a transmit authority, and opening a real serial port is
refused unless every fixture has been promoted to tier `[A]` by a Phase 1 capture. Gating only the
encoder would leave a real port open with a real `SerialStream` behind it. A CI job asserts the gate
is still closed on every run, so opening it is a dated, reviewable act rather than a flag someone
flips.

Ring 3 **does** open valves — that is what it is for, and they are models in the test process behind
pseudo-terminals. What no test can do is open a *real* one, and ring 3 asserts at the end of every
run that the daemon opened pseudo-terminals and nothing else.

## What runs, with no hardware

```
./scripts/test.sh            809 tests, fmt, clippy, docs, graph audit, gate, oxfmt
./scripts/e2e.sh             the real kdtvd binary over PTYs, 7 assertions, ~38 s
./scripts/e2e.sh --pi-sim    the same, ARM64 under qemu-user
./scripts/emulate.sh         the whole system up, until Ctrl-C
./scripts/build.sh --pi      aarch64 cross-build
./scripts/deploy.sh <host>   validate on target, keep the old binary, roll back on failure
```

## Ring 3

Seven assertions, all made against the **transcript** — the bytes the daemon actually transmitted —
rather than against what the daemon reports about itself. A service that believes it is off while
transmitting an open frame passes a state assertion and fails this one.

The boot sequence; the documented cadence measured on the wire; one transaction in flight per link;
a zone-1 fault leaving zone 2 and steam untouched; the independent probe stopping water both by
reading hot and by going silent; `SIGTERM` putting an all-off on the wire *before* the process is
gone; and the gate still closed at the end.

Checked for vacuity rather than trusted: pointing `KDTV_E2E_DAEMON` at `/bin/true` makes all seven
fail, including the gate assertion — the one most likely to pass because nothing happened.

## Design decisions worth reviewing

- **`Cx2` and `Fx2` are unrelated types** with no `From`, no `Deref` and one conversion function that
  `clippy.toml` forbids calling outside the steam encoder. Fx2 220 is 110 °F; the same byte read as
  Cx2 asks a valve for 110 °C, and range checking does not catch it because both are in range for
  their own encoding.
- **Denial is by absence of a variant, not a runtime check.** Ten Saturn control bytes and thirteen
  DTV+ opcodes are unspellable. Power clean needed a different mechanism: `0xCC` is a *payload
  value* of an allowlisted command, so it is denied by the operation-state enum having only `Off`
  and `On`.
- **Write opcodes are an explicit table, never `read | 0x80`** — `0x40 | 0x80` is `0xC0`, the
  calibration write, which would burn a valve's EEPROM.
- **The Fahrenheit ceiling is checked before rounding**, so 108.6 °F is refused rather than quietly
  becoming the 108.5 that `Cx2` can represent, and rounding is downward. 113 °F — the controller's
  own configured maximum — is refused, because `DISCLAIMER.md` says that maximum is above the scald
  threshold and is not a safe bound.
- **Contradictions are plumbed, not decided** — master address `0x00` vs `0x10` (I5), retries 3 vs 5,
  DTV+ tick 150 ms vs 500 ms, whether `SET_DEV_PARAM` is acknowledged, which opcode carries a steam
  status reply. Those five are what a packet capture would settle.

## Findings from building it

**No frame the steam encoder can produce needs byte stuffing.** Verified by enumerating all 7,200
reachable frames. So an escape byte in a TX trace is evidence that something built a frame this
encoder did not.

**Three adversarial reviews of `kdtv-service` found 26 defects in code that passed every check.** The
two that mattered most: a zone whose independent probe had *never* produced a sample never tripped
starvation, so it reached ready and opened water with the entire interlock inert; and a terminal link
error closed the port *before* driving the escalation, so the all-off the kernel ordered was built
and silently discarded. Both were invisible to the test suite — the second had a test that asserted
the resulting phase and never that a frame reached the wire.

**Nothing paced commands**, so an API client looping `stop()` could put ~100 frames/s on a bus
specified for ~2/s. That is [I1](INVESTIGATIONS.md#i1--the-shower-stops-mid-use) through a different
door, in the replacement for the controller I1 was about.

**Several checks were green and not checking.** `scripts/test.sh` claimed parity with CI twice
without having it; a `PhantomData<*const ()>` documented as a `!Clone` marker was really a `!Send`
marker, guarded by a test that accepted `i32`; two `hard = true` logging requirements were covered by
tests that could not fail. Each is recorded in the commit that fixed it and in
[STORY-LOG.md](STORY-LOG.md).

## What a green suite does not prove

The emulated valves are built from the same `[C]` documents the encoder is. A passing run is internal
consistency between our decoder and our model — not evidence about a real valve. Phase 1 capture,
Phase 2 bench and Phase 3 measurement are what close that gap.
